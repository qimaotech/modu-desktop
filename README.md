# Modu Desktop

Modu Desktop 是一款专为 macOS 打造的原生客户端，帮助开发者统一管理跨仓库开发工作区。

Modu 按任务组织多个仓库的独立工作树，方便开发者切换任务，并在外部开发工具中打开相关项目。

![Modu](./.github/assets/modu-mock.png)

## 主要功能

- 管理工作区中的多个 Git 仓库，支持批量添加与更新。
- 创建、编辑和删除跨仓库的 Worktree Group。
- 查看工作树更改与提交，在 Agent、编辑器、终端或 Git 工具中打开当前目录。
- 通过 YAML 导入导出工作区结构，支持中文与英文界面。
- 使用配套的 `modu-cli` 和工作流 skill 管理工作区。
- 通过可配置的全局快捷键显示或隐藏窗口，默认使用 `⌃⌥Z`。

## 工作区如何组织

工作区本身也是 Git 仓库，可维护跨仓库共用的文档、提示词和工作流。业务仓库与任务分组按以下结构组织：

```text
example-workspace/
├── repositories/                # 主仓库的本地副本
│   ├── order-service/
│   └── storefront-web/
└── worktrees/
    └── feature-checkout/         # 一次开发任务的工作树分组
        ├── order-service/
        └── storefront-web/
```

分组根目录是工作区仓库的 linked worktree，成员目录分别是所选主仓库的 linked worktree。同一仓库可以参与多个分组，各自保留独立的工作目录与分支，并共享该仓库的 Git 数据。

创建时，分组根目录和成员使用与分组同名的分支；已有可用的同名本地分支会被复用。新建根目录分支从工作区当前提交开始；新建成员分支优先基于本地已知的同名远端分支，否则使用本地已知的远端默认分支。

创建分组不会自动更新主仓库，已有分组也不会自动同步工作区文档或内置 skill。选中分组打开 Agent 或编辑器，即可从同一个目录处理本次任务涉及的多个仓库。

## 开始使用

当前安装包适用于 Apple Silicon Mac。可从 [Releases](https://github.com/qimaotech/modu-desktop/releases) 下载 DMG，也可从 [GitHub Actions](https://github.com/qimaotech/modu-desktop/actions/workflows/ci.yml) 的构建产物获取；打开后将 `Modu.app` 拖入 Applications。系统要求见对应发布说明。

Modu 默认在启动或重新激活时自动检查 GitHub 最新正式版本，每天最多一次；可在更新窗口左下角关闭“自动检查更新”。后台检查没有新版或网络失败时不提示，发现新版后会在当前操作结束、App 处于前台时显示更新窗口，点击版本变化中的目标版本号可查看该版本的发布说明。也可随时通过菜单栏 **Modu → 检查更新…（Check for Updates…）** 手动检查。

自动检查不会下载或安装更新。点击“安装并重启”后，Modu 会下载并校验安装包，完成当前操作的退出处理后替换应用并请求启动新版，同步更新内置 CLI。原应用未能及时退出时，会显示错误并恢复为可重试状态。安装后不会自动回退旧版本；如果新版未能启动，可从原安装位置手动重新打开。应用所在文件夹需要允许当前用户写入。

当前为测试包，采用 ad-hoc 签名，尚未做 Developer ID 签名与 Apple 公证。

若 App 因下载隔离标记而无法打开，确认安装包来源可信后，可在终端运行以下命令移除隔离标记，再重新打开 Modu：

```bash
xattr -dr com.apple.quarantine /Applications/Modu.app
```

1. 启动 Modu，按引导安装 CLI 并选择工作区目录，首次使用建议选择专用的新目录。
2. 通过仓库 URL 添加 Git 仓库，或在添加窗口的“导入”菜单中选择本地仓库或 YAML 文件，勾选后从远端克隆到工作区。本地导入不迁移原目录中的开发环境或未提交改动；仓库访问沿用本机 Git 认证配置，需提前准备相应访问权限。
3. 按需更新主仓库，再创建 Worktree Group（工作树分组），填写分组名称并选择本次涉及的仓库。名称须是单个目录名且符合 Git 分支命名规则，例如 `feature-checkout`，不能包含 `/` 或空格。
4. 选中分组，通过工具栏在已安装的 Agent、编辑器或终端中打开；只处理一个仓库时，选中对应成员。不同任务可保留不同分组，切换目录时保留各自的改动。
5. 在各仓库中完成开发、提交、推送和合并后，核对需要保留的内容，再清理不再需要的成员或分组。

Git Browser 以本地 `origin/HEAD` 所指的远端追踪分支为基准。选中仓库或工作树、刷新详情以及后台预加载均只读取本地 Git 状态和已有远端引用，不自动 fetch，也不获取工作区锁；“独有提交”列出当前 HEAD 相对本地基准引用的独有提交，没有独有提交时隐藏卡片。基准引用缺失时显示为不可用，文件更改仍可查看。通过外部 Git 工具或“更新主仓库”操作同步远端后，重新读取详情会使用更新后的本地引用。CLI 查询也不触发 fetch。业务开发、运行、提交与合并在外部工具中完成，各仓库独立操作。

基准分支中存在当前 HEAD 尚未包含的提交时，分支卡片显示“落后 N 个提交”，点击可查看全量提交列表；浮层按内容调整宽度，长文字截断，超高列表滚动。当前分支可以同时拥有独有提交并落后于基准，提示不会自动合并或修改当前分支。

## CLI 与 Agent

引导会创建 `~/.local/bin/modu-cli` 符号链接，直接指向当前 App 内置的 CLI，该目录需在登录 shell 的 `PATH` 中。App 路径不变时，更新 App 后 CLI 会自动跟随，无需重新安装；旧版复制安装首次迁移、移动 App 后，需在引导中重新安装以修复链接。在工作区根目录运行，例如：

```bash
modu-cli workspace inspect
modu-cli worktree create feature-checkout --repo order-service --repo storefront-web
```

上例需先添加对应仓库。`--repo` 使用仓库 URL 末段去除 `.git` 后缀得到的 ID（主仓库目录名）；自定义显示名称不改变 ID。不同 URL 派生的同名 ID（忽略大小写）不能共存。

CLI 会从当前目录向父目录查找已登记的工作区；在工作区外运行时，通过 `--workspace <工作区根目录>` 指定。

`workspace inspect` 默认输出从工作区到各工作树的 ASCII 目录树，静默跳过失效资源，不列出工作树内的代码文件。`--json` 成功时直接返回嵌套的 `type`、`path`、`children` 节点：根路径为绝对路径，子路径相对直接父目录；工作树叶子的 `children` 为 `null`。类型固定为 `workspace`、`auxiliary-directory`、`group`、`main-worktree`、`linked-worktree`。工作区本身无效或取消时仍返回错误，JSON 错误沿用操作结果封装。

`repo list`、`worktree list` 保留逐项状态与错误输出，`--json` 仍返回包含 `items` 的操作结果，可从中读取业务 ID。CLI 查询和 YAML 导出均读取登记快照，不清理记录、不 fetch，也不等待工作区锁；YAML 导出保留完整登记配置。登记快照与目录状态可能在并行操作期间发生变化，查询结果不会自动修复或接管资源。

桌面端和 CLI 可以同时使用。同一工作区需要加锁的操作发生冲突时，每隔 500 毫秒重试一次，最多重试 10 次；仍无法获取锁时返回 `workspace-lock-timeout` 超时错误，支持取消的操作在等待期间也可以取消。查询和仓库更新不获取工作区锁，不同工作区的写操作使用独立的锁。

CLI 提供工作区检查、仓库列表/添加/删除、分组列表/创建/编辑/删除；工作区初始化与切换、批量导入、更新主仓库及 YAML 导入导出通过 App 操作。更多用法查看 `modu-cli --help` 及各子命令的 `--help`。

工作区安装内置工作流 skill 后，可从工作区根目录启动 Codex，默认允许根据任务自动调用，也可通过 `$modu-workflow` 显式调用，协助管理仓库和分组。创建前会确认分组名称和完整仓库列表；删除或移除成员前会检查影响范围与风险。

### 工作区文件与自动提交

Modu 会自动修改以下工作区文件，并在内容相对 HEAD 有变化时自动提交到工作区根仓库：

- **`.gitignore`**：初始化、打开或重新加载工作区，以及添加或导入仓库时，按需补充忽略规则。自动提交以整个文件为范围，因此可能一并提交你的手动修改。
- **内置 skill**：打开或重新加载工作区时，会丢弃 `.agents/skills/modu-workflow/` 下 `SKILL.md` 与 `agents/openai.yaml` 在工作树和暂存区中的未提交改动，同步内置版本并按需提交。请勿修改这两份托管文件。

App 启动恢复工作区、切换工作区和手动重新加载会执行上述维护流程。工作区加载失败页面提供“重新加载”按钮，执行期间不可取消，退出会等待本次加载收尾。回到前台及管理操作结束后的自动刷新读取工作区记录并更新 Git 详情，不执行目录修复、记录清理或内置工作流同步。自动提交信息附带 `Auto-committed-by: Modu`；请预先配置本机 Git 提交身份及所需的签名环境。

需要自定义流程时，建议在工作区根目录新增 `.agents/skills/modu-workflow-addon/SKILL.md`，通过独立的 `modu-workflow-addon` skill 维护自定义约定与步骤。

## 使用须知

- **本地扫描**：支持多选文件夹。直接选择 Git 仓库目录时，会额外检查其直接子目录；从普通目录递归发现 Git 仓库时停止向下遍历。依赖、构建产物目录和符号链接会被跳过。远端优先选择 `origin`，没有 `origin` 时仅使用唯一远端；无法确定远端、所选远端不可访问或默认分支无效的仓库不会列出，也不会尝试其他远端。
- **添加与导入**：先在本次私有临时目录中完成克隆准备，准备过程不持工作区锁；发布到正式位置、更新登记和自动提交时加锁并重新检查当前状态。普通批量导入逐项准备、发布，后续失败时保留已发布仓库；空工作区 YAML 导入先准备全部仓库，全部成功后才重新确认工作区为空并发布。YAML 准备阶段失败或取消不会登记仓库，发布开始后的部分成功可能保留。临时清理只处理本次创建的目录；清理失败或正式路径的登记保存结果不确定时，会报告保留路径和实际效果。
- **工作区记录**：管理记录保存在本机 `~/Library/Application Support/Modu/`，绑定工作区路径，不随工作区 Git 提交分享。直接移动或重命名工作区目录不会自动迁移记录。打开或手动重新加载时会移除目录已消失的资源记录；自动刷新、CLI 查询和 YAML 导出不会清理记录，也不会自动接管磁盘上未登记的仓库或工作树。
- **更新主仓库**：按本地 origin/HEAD 记录的默认分支 fetch，再直接合并对应的远端追踪引用，只允许快进；有本地改动或未处于该分支时会跳过。更新不获取工作区锁，并行操作引起的 Git 锁冲突、路径变化或分叉会按实际结果报错。已有分组的任务分支需自行同步基准。
- **分享结构**：在“设置 → 配置”中导出 YAML，可在空工作区中导入仓库清单和分组关系。YAML 不包含代码、提交历史、未提交改动或当前分支状态，不能作为备份恢复。
- **清理任务**：删除成员或整个分组会永久移除对应工作树及其当前本地分支，包括复用的分支和未合并提交；删除主仓库还会移除关联成员，再将主仓库目录移至废纸篓。确认前请核对删除预览。
- **删除预览**：删除及编辑分组的移除预览读取登记快照，在工作区锁外收集风险；确认执行时重新加锁、读取当前记录并复核目标和安全条件。
- **取消与失败**：批量操作取消或部分失败后，已完成的效果可能保留，请按结果列表核对并处理剩余项目。
- **Submodule**：当前不支持为包含 Git submodule 的仓库创建分组成员工作树。

本地构建与测试命令见 [Taskfile.yml](Taskfile.yml)，版本变化见 [更新日志](CHANGELOG.md)。
