## 0. 文档职责

本文定义产品范围、数据、业务行为、安全边界和验收。[DESIGN.md](DESIGN.md) 定义界面、交互、文案和原型索引；[AGENTS.md](../AGENTS.md) 只提供开发入口和工程约定，不重复业务规则。

优先实现正常使用的完整流程，以及应用自身操作失败时的安全停止和真实反馈。异常资源允许明确报错，不要求每种异常都有应用内修复入口。原型只提供视觉参考，不能扩展本文的功能范围。

## 1. 产品范围

Modu 是管理多仓库和跨仓库 linked worktree 的 macOS 原生工具。核心流程为：**选择工作区 → 添加仓库 → 用户提交工作区文件 → 创建 Group → 在外部工具中开发 → 查看状态 → 删除不再需要的 Group**。

### 1.1 保留的核心功能

| 能力 | v0.1 范围 |
| --- | --- |
| 工作区 | 首次设置、打开和切换；根目录为 Git 仓库，同时只激活一个 |
| 仓库 | 单个添加、从 YAML 批量添加、删除、手动批量更新（只快进 Pull） |
| Worktree Group | 以工作区仓库的 worktree 为根，跨仓库创建、编辑和删除成员 |
| 外部工具 | Agent、Git GUI、编辑器、终端打开当前上下文 |
| Git Browser | 工作树摘要、未提交 Changes、相对 Base 的 Commits |
| 设置 | 中文/英文、选择与切换工作区、YAML 导入空工作区及导出 |
| 命令行 | 与 GUI 共用 Core 的 CLI，以及 Codex 工作区级 skill |

目标规模为 5–20 个主仓库、约 5 个活跃 Group、最多约 30 个成员 linked worktree，另有每个 Group 的根 worktree。仅在选中成员仓库的主工作树或 linked worktree 时加载其提交历史，每次最多加载 30 条。

### 1.2 明确不做

- 不替代 Agent、编辑器或完整 Git GUI；不提供 staging、commit、merge、rebase、逐行 diff 或 Agent 编排。
- 不提供配置与文件双向同步、缺失资源自动补齐、磁盘资源接管、目录迁移或覆盖式 YAML 导入。
- 不提供独立 Fetch、自动抓取或自动 Pull；启动和 App 激活只刷新本地状态，不触发网络更新。
- 不提供配置修复中心、跨重启任务续跑、操作 journal、整体回滚或 Git/index/工作文件备份。
- 不监测或修复用户在操作期间对目录、配置和 Git 登记的并发修改；不管理配置外资源。
- 不提供自定义工具、团队云同步、正式签名公证与自动升级。内置 skill 只保证 Codex，Claude Code 仅作为启动目标。

这些限制不妨碍正常代码编辑与 Git 开发。资源异常时保留现场并说明原因，用户处理后重新加载；不为消除报错扩大文件操作范围。

## 2. 系统边界

`ModuDesktop` 和 `modu-cli` 是薄入口，共享 `ModuCore` 的配置、Git、文件系统、worktree 和外部工具服务。GUI 负责展示与意图，CLI 负责参数与输出；业务规则只在 Core 实现一次。

- 使用 SwiftUI/AppKit；当前本地构建的最低系统版本以 Xcode 工程部署目标为准，使用 macOS 26 原生控件。
- 关闭 App Sandbox，访问用户选择的工作区；不隐式安装 Git 或开发工具。
- Git 调用系统 `git`；CLI 使用 Swift Argument Parser，YAML 使用 Yams，私有记录使用 JSON，不引入数据库或后台守护进程。
- 复用用户的 SSH、credential helper、hooks 和 Git 配置；认证、进程和输出边界见第 8 节。

| Git 场景 | 支持范围 |
| --- | --- |
| 工作区根仓库 | 普通非 bare 主工作树；无需远端，创建 Group 前需有效提交及已提交的忽略规则 |
| 有有效远端默认分支的普通非 bare 仓库 | 完整核心流程 |
| 空远端或无有效远端 HEAD | 添加/更新失败，不猜测默认分支或提供手动 Base |
| submodule | clone 不递归初始化；显示父仓库摘要，不展开内部 Changes；不为含 submodule 的仓库创建 linked worktree |
| LFS / filter | 使用现有环境，失败如实报告，不安装或维护依赖 |
| locked worktree | 可读、可打开；修改/删除时失败，不自动解锁或加倍 force |
| sparse checkout | 不管理稀疏策略，按 Git 返回的真实状态读取 |

## 3. 数据与配置

### 3.1 工作区结构与私有记录

```text
<workspace>/
├── .git/
├── .gitignore
├── AGENTS.md                       # 可选，由用户纳入版本管理
├── repositories/<repo-name>/
├── worktrees/<group>/              # 工作区仓库的 linked worktree
│   ├── .git                       # Git 创建的登记指针
│   ├── .gitignore                 # 从工作区仓库的提交检出
│   └── <repo-name>/               # 成员仓库的 linked worktree
└── .agents/skills/modu-workflow -> Application Support 中的受管 skill
```

工作区记录保存在当前用户的 `Application Support/Modu`，包含 `version: 1`、规范化绝对根路径 `root`、`repositories` 和 `groups`。它是管理清单的唯一事实源；路径由根、仓库身份和 Group 推导，不在成员中重复保存。工作区目录不存 Modu 配置或识别标记；根目录已有 Git 仓库时复用，否则在首次启用时初始化，规则见第 4.1 节。

App/CLI 按同一规范化根路径定位记录和工作区锁。根路径解析符号链接并遵循文件系统大小写语义；有效记录中的工作区根不能互相嵌套。不另建历史登记库；当前工作区引用的记录丢失属于配置错误，其他无记录目录按第 4 节的空目录条件决定能否初始化。

全局偏好保存当前工作区引用、语言、工具默认值及窗口偏好。Git 状态、缓存和操作进度只在内存中保存；不保存自动更新开关、更新间隔或调度时间。

### 3.2 仓库与成员规则

- 仓库只保存 `url` 和可选展示名 `name`。URL 接受 HTTPS、SSH URL 或 SCP 风格 SSH；拒绝本地路径、其他协议及内嵌密码/token。非法输入在 Git 或文件操作前拒绝。
- 从 URL 最后路径段去除末尾 `/` 和一个 `.git` 后缀得到仓库名；查询与 fragment 不参与名称推导。仓库名匹配 `[A-Za-z0-9][A-Za-z0-9._-]*`，不能为 `.` 或 `..`，在工作区内忽略大小写唯一。不同远端的同名仓库不支持，展示名不改变身份或路径。
- GUI 常规表单只添加、删除仓库，不提供 URL 原位修改。Base 不写入配置，读取语义见第 10 节。
- Group Name 原样保存，必须是合法单段目录名，不能以 `-` 开头，作为 `refs/heads/<group>` 通过 Git ref 校验；按 Unicode 规范化及工作区文件系统的大小写语义唯一。
- Group 包含带时区的 RFC 3339 `created-at` 和成员集合；普通编辑保留创建时间。私有记录与 YAML 均以 `repositories` 仓库名列表表示成员，引用已声明仓库，同一 Group 不重复引用。Group 根 worktree 是独立资源，创建成员部分失败或移除最后一个成员后允许保留空集合；YAML 可导出和重建这种 Group。
- Group 根 worktree 与新增成员的初始分支名统一使用 Group Name，GUI、CLI 和 YAML 导入遵循同一规则，不提供分支覆盖。私有记录与 YAML 均不保存初始分支、当前分支或分支归属。名称仅作为明确的分支名使用，不解释为选项或 checkout shorthand；实际分支占用以各仓库的 Git 登记为准。删除 worktree 时一并删除其当前检出的本地分支，见第 7.3 节。

### 3.3 加载与保存

配置的版本、类型、未知/重复字段、身份、成员引用及路径/ref 必须有效。已有记录不可读或无效时停止该工作区操作，不覆盖为空配置、不从目录反推清单；当前工作区引用的记录缺失也不自动初始化。

配置读写使用同一工作区锁；锁忙为 `workspace-busy`，不当作配置损坏。修改从读取到收尾持续持锁；每次保存校验完整候选，在记录同目录写临时文件后原子替换，保存成功才更新界面。资源的完成边界见第 8 节。

启动、打开、Reload 和 App 激活时重读配置并检查声明资源。检查只读，不联网、不自动修改声明或文件；忙时暂缓刷新。配置外目录不进入管理列表、不接管、不主动清理；关联分支删除与失败清理分别按第 7.3、8.2 节处理。删除仓库的阻断信息可列出相关 Git worktree 登记路径，见第 5.2 节。

### 3.4 YAML 导入与导出

设置中的 YAML 导入用于重建仓库及分组结构，以下规则仅适用于该入口；Add Repository 中从 YAML 批量添加仓库见第 5.1.1 节。工作区 YAML 不保存 Group 根或成员分支，也不包含工作区仓库的内容和历史。导入以分组名作为根 worktree 与成员的初始分支名，按目标机器已有的 Git 引用重新创建环境，不恢复外部切换后的分支状态，也不保证恢复原提交位置；未推送的分支提交不会随文件迁移。只包含以下字段，沿用第 3.2 节校验：

```yaml
version: 1
repositories:
  - url: git@github.com:team/frontend.git
    name: Web Console
groups:
  feature-report:
    created-at: "2026-08-26T10:30:00+08:00"
    repositories:
      - frontend
```

- 导出当前有效配置，不包含 root、内部路径、Base、全局偏好或运行状态；默认文件名 `<workspace-name>.yaml`，不保留注释和排版。
- 导入只允许当前有效工作区的清单为空，且 `repositories/`、`worktrees/` 都为空或不存在。隐藏/未受管条目也算非空；目录不可读、不是普通目录或为符号链接时拒绝，不移动已有内容。
- 先完整校验 YAML 和本地前置条件。包含 Group 时，在 clone 前检查目标工作区仓库已有提交，且各 Group 将检出的提交满足第 7.1 节忽略与路径条件；不满足时提示用户按导入仓库名准备并提交根 `.gitignore`，不开始导入。通过后创建缺失的标准目录，按仓库→Group 根 worktree→成员复用普通创建流程，逐项成功后保存；Group 的创建时间与成员列表取自 YAML，初始分支名由分组名推导。不预先保存整份目标清单。
- 失败或取消保留已完成项，未完成项不成为声明；结果列出未完成的仓库、分组和成员。有已完成项时不能原地重新导入。排除失败原因后，通过 Add 添加剩余仓库、Create 创建尚未建立的 Group、Edit 为已有 Group 补齐成员；新增成员仍使用分组名作为初始分支名，不改变已完成成员的 checkout。也可选择另一个空工作区导入；不为部分导入设计续跑协议。
- 文件选择、校验和执行固定同一工作区；期间禁用切换和重复提交。无有效工作区时导入/导出不可用。导出与校验失败不影响当前清单。

## 4. 工作区与设置

### 4.1 首次设置和切换

首次设置依次检查 CLI、选择候选目录、点击 Continue 初始化或加载工作区。CLI 必须安装并通过可用性检查后才能继续；未安装或安装失败时停留在 CLI 步骤，允许重试或退出，不提供跳过。skill 安装失败允许跳过，不阻断 GUI；目录选择和候选检查无副作用。

- 有对应记录的目录：先校验记录和根仓库，再补齐第 4.1.1 节的标准目录忽略规则，加载成功后才切换；错误不改变当前工作区。已登记工作区的 Git 元数据缺失或损坏时不重新初始化。
- 无记录的目录：仅在两个标准资源目录为空或不存在时允许初始化。Continue 时复用根目录已有的普通非 bare 主仓库；不存在仓库且不位于其他 Git 仓库内部时，在根目录执行 `git init`。随后补齐标准目录忽略规则、创建缺失目录和空记录；其他根目录内容保留。成员仓库不能通过首次设置自动接管。
- 路径不可写、工作区嵌套、候选目录只是其他 Git 仓库的子目录、是 bare/linked worktree 或标准目录类型不正确时拒绝初始化。失败报告实际结果，已初始化的 Git、已修改的 `.gitignore` 和空目录可保留，不删除用户原有内容。
- 成功加载后保存当前工作区引用。取消候选选择保留原工作区；正常切换入口位于 Settings。

CLI/skill 的版本化内容位于 Application Support。CLI 只在登录 shell PATH 中的用户所有、可写且非 group/world-writable 目录安装受管链接；无合适位置时使用 `~/.local/bin` 并说明 PATH，不修改 shell 配置。已有非 Modu 同名目标不覆盖。

CLI 安装成功必须同时满足：受管可执行文件能够正常运行，且当前用户登录 shell 通过 PATH 将 `modu-cli` 解析到该文件，按解析符号链接后的真实路径比较。检查不依赖已初始化的工作区。仅创建文件或链接不算完成；PATH 未包含安装目录、命令被其他同名目标遮蔽或运行检查失败时，停留在 CLI 步骤说明原因，由用户处理后重试。重试重新读取登录 shell 环境并检查。

skill 只安装为当前工作区 `.agents/skills/modu-workflow` 链接；仅更新指向 Modu 的旧链接，不覆盖同名文件或第三方链接。不创建用户级链接，也不向 Group、主/linked worktree 注入文件。从工作区根启动 Codex 才保证发现该 skill。

### 4.1.1 工作区 Git 与忽略规则

选择工作区并点击 Continue 时，按 Git 的忽略语义检查根 `.gitignore` 是否覆盖根目录下的 `repositories/`、`worktrees/`；缺失时创建文件或在末尾追加 `/repositories/`、`/worktrees/`。每次添加仓库还检查并补齐 `/<repo-name>/`，使新 Group 中的成员目录可被该文件忽略。已生效的规则不重复追加，保留已有内容；不改写 `info/exclude` 或全局 Git 配置。`.gitignore` 为符号链接、非普通文件或不可读写时停止相关操作，不能把检查失败当成规则缺失。

忽略规则不能排除已经跟踪的文件。发现标准资源路径已被根仓库跟踪时停止启用；成员名与 Group 将检出的受版本控制文件冲突时停止创建，不自动移除跟踪或覆盖文件。

Modu 只初始化 Git 和补齐忽略规则，不自动暂存或提交。用户自行完成首次提交，并提交需要进入 Group 的 `.gitignore`、文档及开发配置。没有提交不阻止启用工作区和添加仓库，但创建 Group 前必须满足第 7.1 节检查；根仓库不要求配置 origin，也不参加批量更新仓库。

### 4.2 资源不可用

| 情况 | 行为 |
| --- | --- |
| 工作区根不存在 | 阻断当前工作区，提供重新选择或退出，不自动创建原根或迁移路径 |
| 工作区根 Git 元数据缺失、损坏或类型不支持 | 阻断依赖根仓库的修改，说明原因；不自动重新初始化或重建已有 Group |
| 配置不可读、无效或当前引用的记录缺失 | 阻断并说明文件及原因，允许 Reload、选择其他工作区或退出，不覆盖记录 |
| 声明目录缺失，或 Git 登记、实际 HEAD、origin、权限不符合要求 | 对应资源显示 Unavailable 和原因，独立可用资源仍可使用；有效的 detached HEAD 不属于异常 |
| Base 不可用 | 只影响 Base 摘要和依赖它的操作/Commits，不隐藏可读取的 Changes |

不提供 Sync Configuration / Sync Files。用户在外部处理原因后 Reload；正常删除仅在第 7、8 节前置条件成立时可执行，不绕过损坏的 Git 登记。主仓库缺失时成员显示依赖不可用，不承诺重新 clone 能恢复现存 linked worktree。

不持续弹出资源修复选择，不自动移除缺失声明。配置修复、重新登记非空目录和历史记录恢复不属于 v0.1；错误说明当前限制与可用动作。

可用性按操作判断：Base 缺失不单独阻止更新，仍按第 6 节检查更新条件；主工作树 dirty 不阻止创建独立成员，仅新增分支需要的起点不可用时阻止该次创建。工作区的未提交内容不带入 Group，首次提交与忽略条件单独检查。Group 根 worktree 的可用性通过工作区仓库的 Git 登记判断，不要求 origin；其异常不遮蔽仍可读取的独立成员，但阻断依赖根目录的新增。Group 编辑只预检新增和移除项，未改变的异常成员不阻止其他成员调整；不因某一项异常禁用整个工作区。

### 4.3 全局设置

- 语言仅中文和 English，首次按系统首选语言选择，之后使用保存值；立即更新界面，路径、分支和用户内容不翻译。
- 操作、取消和收尾期间禁止切换工作区。Reload 或退出先取消可取消步骤、等待必要收尾；存在保留效果时先展示结果。

## 5. 添加与删除仓库

### 5.1 Add Repository

输入 URL 与可选 Display Name，先校验输入、名称冲突和本地路径条件，再按第 4.1.1 节检查并补齐根 `.gitignore` 的 `/<repo-name>/` 规则。之后检查远端支持范围和默认分支，完整历史 clone 到本次创建的临时目录，确保首次 checkout 有效远端默认分支及本地 origin/HEAD 正确，再改名到目标路径并保存声明；目标占用不覆盖。

忽略规则、资源与配置都完成才成功。失败清理本次未保存的新目录，不删除原有内容；已追加的忽略规则保留并在结果说明，删除仓库时也不自动移除规则。重复 CLI add：同一 URL 且 name 未改变、资源有效时仍检查忽略规则，除此之外无修改；资源不可用时报告错误，不解释为补齐。省略 name 保留已有值，其他同身份冲突报 `repository-conflict`。

### 5.1.1 从 YAML 批量添加

Add Repository 提供 Import YAML，选择一个 `.yaml` 或 `.yml` 文件后自动解析并依次添加识别出的仓库，无需逐条填写或再次确认。可向已有仓库的有效工作区追加；只提取仓库 URL，不导入 Group、展示名或其他配置，不受第 3.4 节的空工作区条件限制。

- 不要求固定字段或 Modu 配置格式。解析单个 YAML 文档，递归遍历映射值和列表元素；仅将去除首尾空白后完整符合第 3.2 节 URL 规则的字符串作为候选。不从键名、注释、命令或说明文字中截取 URL，不要求地址以 `.git` 结尾。普通值忽略；只解析数据，不执行自定义标签。文件不可读或 YAML 解析失败时不开始添加；没有合法 URL 时说明原因，不修改工作区。
- 本地校验只能确认 URL 格式；远端是否为可访问且受支持的 Git 仓库，仍复用普通添加的远端检查。凭据 URL 拒绝，错误信息不得暴露其中的密码或 token。
- 相同 URL 去重后按文件中的首次出现顺序处理。已登记同 URL 且资源有效的仓库复用普通添加检查（含忽略规则），记为已存在，保留展示名且不重复 clone；资源异常记为失败，不自动修复。派生仓库名相同但 URL 不同的候选均记为冲突，不任意选择其中一个；与已登记仓库冲突同样不覆盖。不推断 HTTPS 与 SSH 地址指向同一仓库。
- 复用普通添加流程和同一工作区锁，逐个检查并补齐 `.gitignore`、clone、保存，保存成功才进入侧栏。单个 URL 的名称/路径冲突或远端失败记录结果后继续其他独立仓库；工作区、忽略文件或配置保存等共享条件失败时停止后续项。取消按第 8.2 节停止并收尾，保留已保存仓库及实际产生的忽略规则修改。
- 文件选择、解析与执行固定同一工作区，执行期间禁止切换或重复提交。结果区分已添加、已存在/重复、失败和未处理，不把全部跳过报告为添加成功。重新选择同一文件仍按现有状态检查，已添加项不重复 clone；不保存导入任务或新增专用 CLI 命令。

### 5.2 Delete Repository

主目录存在时，确认前只读列举该仓库的全部 Git worktree 登记，按规范化路径与配置成员比对。除主工作树外，任何未对应到该仓库配置成员的登记都阻断整次仓库删除，包括目录缺失或 locked 的登记；返回 `unmanaged-worktree` 并列出登记路径。登记读取失败或归属无法确认也停止，不当作没有外部依赖。阻断时不删除任何关联成员、分支、主目录或声明；用户在外部处理后重试，不提供强制继续、接管或自动清理。

通过预检后，一次确认包含主目录、配置内关联成员、本地分支处置和风险。确认后持工作区锁重新检查上述条件，通过后才开始任何删除：先按第 7.3 节逐个删除关联成员，再将主目录移入系统 Trash，最后移除仓库声明；任一步失败停止并保留已完成结果。GUI 与 CLI（含 `--execute`）使用相同前置检查，删除授权不绕过依赖检查。

主目录已缺失且没有需处理的关联成员时，可明确确认只移除声明，不执行文件或 Git 资源删除；不可读或 Git 错误不能当作缺失。主目录移入 Trash 后保存失败，报告实际 Trash 位置和仍保留的声明，不自动移回或重建。

## 6. 更新仓库（Pull）

更新是用户手动触发的批量操作，采用 Git Pull 的获取远端更新并只快进语义；获取远端引用仅为更新的内部步骤，不提供单独执行入口。只针对配置内主仓库，按配置顺序串行处理，不修改 linked worktree 的文件和 checkout；共享 refs 仍会变化。某仓库普通失败或跳过不影响其他独立仓库。

### 6.1 执行条件与步骤

只更新 clean、非 detached 且当前分支为远端默认分支的主工作树。本地预检为 dirty、detached 或已确认缺失时直接 skipped，不联网；状态读取失败为 failed。当前默认分支以本次获取的远端信息判定，不要求旧的 origin/HEAD 已经有效。

对候选主工作树检查路径、配置、Git 登记及实际 origin 与声明一致，获取并裁剪 origin refs，查询远端 HEAD，验证对应远端跟踪分支有效后更新本地 origin/HEAD。Git 引用更新使用其原子能力，不手工备份或恢复 refs。

以本次确认的默认分支名称和 OID 判断当前分支并执行快进；名称不匹配则 skipped，已获取的引用更新在结果中保留。不反复联网确认远端之后是否又有变化，不重复获取，也不隐式 stash、创建 merge commit 或 rebase。

为固定更新目标并保护 ignored 文件，内部按获取引用、快进两个步骤执行，快进使用 `merge --ff-only --no-overwrite-ignore <OID>`。clean 不表示 ignored 文件可以丢弃，发生覆盖冲突即失败，不另建文件备份。更新失败或取消保留已发生的引用更新和实际工作树效果，不 reset 回退；重新读取并报告真实状态。

### 6.2 互斥、取消与结果

整个更新请求按第 8.2 节持有工作区锁，直到当前进程退出和必要收尾完成；浏览现有内容与打开外部工具不因更新被整体禁用，需要重读配置的刷新遇锁忙时暂缓。取消停止后续仓库，向当前子进程发送终止请求，等待退出与收尾后释放锁；已经更新的引用和工作树不回退。

共享引用可能变化时，使同仓库主/linked worktree 的提交缓存失效，包括后续步骤失败或取消的情况。结果按配置中的仓库顺序汇总，逐项区分已更新、已是最新、跳过和失败；跳过不是已是最新，全部跳过也不报告更新成功。

## 7. Worktree Group

### 7.1 创建

Group Name 与至少一个仓库组成常规创建请求。Group 根目录是工作区仓库在 `worktrees/<group>/` 的 linked worktree，成员是各自仓库在其下的 linked worktree；所有初始分支名均为 Group Name。YAML 允许按原清单重建零成员 Group。

先校验完整请求中可提前判断的名称、路径、依赖、分支占用与 Git 条件，任何本地预检失败都不开始创建：

- 工作区仓库必须有有效 HEAD。根仓库同名本地分支已存在且未被其他工作树检出时复用；不存在时从工作区当前 HEAD 的提交创建，不依赖远端。起点在本次操作中固定。
- 检查根 worktree 将检出的提交中 `.gitignore` 是否覆盖 `/repositories/`、`/worktrees/` 及本次成员目录，且成员路径未被该提交跟踪或占用。没有首次提交或所需规则尚未提交时，提示在外部工具提交工作区 `.gitignore` 后重试；复用分支也以该分支提交为准。其他文件 dirty 不单独阻止创建。
- 成员仓库同名本地分支已存在且未被其他工作树检出时复用；不存在时优先从本地已有的同名 origin 远端跟踪分支建立 tracking branch，否则从有效 origin/HEAD 创建。创建不隐式联网或更新已有工作树；缺少起点时提示先更新主仓库，无法更新则在外部工具处理。
- 目标目录或不属于该有效配置资源的 Git 登记已存在时停止，不接管、覆盖或通过 force 修复。

通过预检后，先创建根 worktree 并保存带空成员列表的 Group，再顺序创建成员；每个成员的 worktree 与分支就绪后立即保存。根资源与记录均成功才发布 Group，成员失败不保存该成员，停止后续成员并保留已保存的根及成员。根创建失败按第 8.2 节清理本次新资源，不删除复用分支；保存成功后即使尚无成员也保留 Group，可通过 Edit 补齐或 Delete 删除。

对已有 Group 的 create 只追加请求中的新成员，不重建根 worktree；已有有效成员直接返回成功，不改变根或成员分支、created-at；已有成员不可用则报错，不自动补齐。

根 worktree 检出所选提交中的全部受版本控制文件，包括已提交的 `AGENTS.md`、`.agents/skills`；未提交修改和未跟踪文件不带入，不另做文件复制或 skill 注入。符号链接只按 Git 保存的链接检出，不复制其指向的外部内容。

根与成员的实际 checkout 均可由用户在外部改变，Modu 读取真实 HEAD、不强制切回，也不将分支状态写入私有记录或 YAML。分组同名分支缺失不影响其他有效分支或 detached HEAD 上的已有 worktree；可用性与删除目标按实际 HEAD 判断，不从分组名推测。

### 7.2 编辑

Group Name 只读，勾选列表表示完整目标成员集合，允许清空成员；根 worktree 和已有成员不改分支。校验完整请求的结构与引用，仅对实际新增/移除项检查执行条件，包含移除时确认一次范围和风险。移除最后一个成员不删除 Group 根 worktree 或其分支。

先逐个新增并保存，全部新增成功才开始逐个移除。任一步失败或取消停止后续操作，已完成项保留；重新打开 Edit 显示当前已保存集合，不保留待续跑目标。

### 7.3 删除成员或 Group

删除只处理配置中的 worktree 及其当前检出的本地分支，不区分分支是新建还是复用。单成员删除只处理该成员；Group 删除包含全部成员及根 worktree，确认中分别列出根与成员的路径、当前分支和风险。确认前从各 worktree 的实际 HEAD 确定待删除分支，读取工作树、ignored 内容和该分支的仅本地提交风险；detached HEAD 没有待删除分支，但仍展示其提交风险。仅本地提交依据本地已知远端跟踪 refs 判断，不额外联网。读取失败不当作无风险，locked 或待删除分支被其他工作树占用时停止。

目录缺失但 Git 登记仍在时，从该登记的 HEAD 判断当前分支；目录和登记均已不存在时仅移除对应声明，不根据分组名猜测待删除分支。登记存在但 HEAD 不可读时停止。确认后，在本次请求的任何新增或删除前重新读取全部待移除 worktree（含 Group 根）的 HEAD，并在本次操作内保留待删除分支；与确认时的分支或 detached 状态不一致时停止，提示重新发起删除。CLI 的 `--execute` 直接授权本次预检确定的目标，不复用上次预览结果。

确认一次后逐成员执行：

1. 使用 `git worktree remove --force` 移除工作树；目录和登记都已不存在时跳过资源移除。Git 错误不使用递归删除绕过。
2. 保存成员移除；最后一个成员移除后保留空 Group。保存失败即停止，不再删除本次确定的分支。
3. 删除执行前确定的当前本地分支，包括复用分支及含未合并提交的分支；分支已不存在视为完成。预检时已确认为 detached HEAD 或目录与登记均缺失的成员没有待删除分支，跳过本步；不删除其他本地分支，远端永不删除。

三步完成才算该成员成功，失败停止后续成员。已删除内容不重建，已移除声明不重新加入；残留分支与实际效果在结果中说明。Missing 不免除对尚存 Git 登记和待删除分支的检查。

删除 Group 时，全部成员成功移除后，才从工作区仓库通过 `git worktree remove --force` 删除根 worktree，随后移除 Group 声明，最后删除预检确定的根本地分支；各步失败立即停止并报告实际效果。任何成员仍有未处理目录或登记，或根目录下发现配置外嵌套 Git 仓库时，不得强制删除根目录。不能先删除根 worktree，否则可能删除内部成员目录却留下它们的 Git 登记。

根 worktree 删除前失败时保留 Group 声明，包括零成员 Group；可重新发起普通 Delete。根已删除但保存失败时保留声明并报告缺失，按上述缺失规则处理；声明已移除后分支删除失败则报告残留分支，不重建 Group。删除仓库或单个成员不会顺带删除空 Group，用户单独使用 Delete Group 清理其根工作树与分支。

## 8. 安全、执行与失败处理

### 8.1 必须保留的安全边界

- 操作路径由有效配置和固定布局生成，检查存在性、类型和符号链接边界；工作区根、资源根及边界外路径不能成为删除目标。
- 新增不覆盖现存资源；主仓库及失败 clone 的清理使用 Trash，worktree 使用 Git 移除能力，不用永久递归删除绕过失败。
- 删除前展示目标与可读取风险并确认一次。确认只授权指定目标；执行时重新读取配置和预检，不依赖历史预览凭证。
- 外部命令使用可执行文件和参数数组；终端适配器传递目录参数并正确转义，不拼接未经转义的 shell 文本。
- 日志、JSON、UI 不暴露带凭据 URL、敏感环境变量或未经整理的完整 Git 输出。

### 8.2 一套执行规则

每个工作区 App/CLI 共用一把锁，配置加载短暂持锁，修改持锁直到进程退出和必要清理完成。预览后释放锁，不在等待用户确认时持锁。锁忙立即返回 `workspace-busy`，后台刷新暂缓；不引入分层锁、长队列或自动重试。

批量请求逐项执行，涉及配置修改的每项完成后保存；更新仓库不写配置，执行结束或取消收尾后汇总结果。新增只有资源和配置均成功才发布；删除按第 5、7 节顺序保存。整个请求全部完成才成功；普通失败和取消保留已完成项，不要求跨文件系统、Git 和配置整体原子性。

失败时仅清理当前未完成项本次创建的新资源，不删除复用资源或已成功项。保存结果不确定时先重读，避免清理已提交资源；重读也失败时停止并保留现场，将结果标为无法确认，不能假定未保存后删除资源。清理失败停止后续工作，说明原始原因及残留路径/分支。各服务使用所需的小型清理函数，不建设通用补偿引擎。

| 失败发生点 | 必须表达的实际结果 |
| --- | --- |
| 新增资源后配置保存失败 | 新增未完成；说明清理是否成功，原配置是否保留 |
| Git 初始化或忽略规则修改后失败 | 说明已初始化的根仓库、已保留的 `.gitignore` 修改；不暗示已提交或自动回退 |
| Group 根已保存、成员创建失败 | Group 根和已保存成员保留；列出未完成成员，可为零成员 Group |
| worktree 已删除但声明移除失败 | 文件已删除、声明仍在；列出尚未删除的实际分支（如有），Reload 不会恢复内容 |
| 声明移除后分支删除失败 | 对应成员或 Group 已移除、分支残留；不自动续删或重建资源 |
| 主目录 Trash 成功但保存失败 | 主目录实际 Trash 位置、声明仍在、资源不可用 |
| 更新仓库中途失败 | 说明各仓库已更新的引用或工作树状态，不暗示完全未发生 |

取消停止后续工作，等待当前子进程退出和必要清理；短暂配置保存与清理不被再次取消打断。全部完成后的晚到取消仍为成功。取消无保留效果可静默，其余情况呈现实际结果。重启只加载当前记录，不恢复历史操作。

### 8.3 网络与进程

网络步骤共用执行器：clone 硬超时 30 分钟，其他网络子进程 60 秒，从启动到退出计时，不随输出重置；超时说明具体步骤，不自动重试或退化为 shallow clone。

认证非交互，不读取 stdin 密码或等待 host key 提示；缺少认证返回明确错误。Git 使用独立进程组，取消/超时先终止、等待 5 秒，仍未退出则强制终止并确认退出。异步读取输出，收尾不能因已脱离进程组的任务持有输出管道而无限等待。

用户 hook/filter/helper 主动脱离进程组的任务及其任意外部副作用不在恢复保证内；不建立全系统进程追踪。

## 9. 外部工具

内置目标：Agent 为 Codex、Claude Code；Git GUI 为 Fork；编辑器为 VS Code、Cursor；终端为 Warp、Terminal。不提供自定义命令模板。

只显示已检测到且适用于当前路径的目标。未选择资源时 Agent 打开工作区根；选中主仓库或 linked worktree 后，四类工具打开该路径。选中 Group 时，Agent、Git GUI、编辑器和终端均打开 `worktrees/<group>/`，不展开为逐成员启动；Fork 管理工作区仓库在该 Group 的 worktree，不汇总成员仓库。Group 详情只显示工具，不加载 Git 摘要、Changes 或 Commits。成员异常不阻止打开仍然有效的 Group 目录；根 Git 状态异常时禁用 Git GUI，其他工具按目录是否可访问判断。另提供始终可达的 Open Workspace in Codex，固定打开工作区根。

每类一个全局默认目标，启动成功后才更新；失败保留原值。通过受支持 CLI 或验证过的 Bundle ID/系统目录打开能力启动；Codex 必须先确认桌面应用已安装，不能借启动触发安装。Claude Code 需要 CLI 和可用终端。路径在启动前重新验证，权限或启动错误明确报告。

## 10. Git Browser

### 10.1 摘要与 Base

成员仓库的主工作树与 linked worktree 共用模型：Path、Base branch、Head branch；工作区仓库及 Group 根不进入 Git Browser。Base 从有效的本地 `refs/remotes/origin/HEAD` 读取，显示如 `origin/main`；确认 origin 与声明一致、引用有效且可解析为提交，缺失时显示不可用，不猜测 main/master、不联网或切换 checkout。detached HEAD 显示 `Detached at <short-sha>`。

### 10.2 Changes

Changes 只展示 staged、unstaged 和 untracked，不包含 ignored；已跟踪文件不因 ignore 规则被隐藏。读取 Git 机器状态并保留 NUL 路径边界，逐路径保存 index/worktree 两阶段状态，不用最终净 diff 替代。

每路径一行，重命名显示新路径并保留原路径；untracked、冲突和未知状态保持各自语义。`A/C` 为 Added、`R` 为 Moved、`M/T` 为 Modified、`D` 为 Deleted。两阶段相互抵消也保留该行，例如 staged Added + unstaged Deleted。

dirty 圆点来自同一次状态结果；读取失败为 Unavailable，不是 clean。Changes 不依赖 Base，merge/rebase 期间仍展示可读取状态。确认为空才隐藏。

### 10.3 Commits 与刷新

Commits 展示 `Base..HEAD`，首次及每次 Load More 最多读取 30 条；没有差异提交时隐藏，不能据此判断工作树是否 clean 或 HEAD 是否落后。Base 或范围不可读时只提示该区域不可用；merge/rebase 本身不构成禁用条件。

提交缓存绑定仓库、HEAD OID 与 Base OID；共享引用变化使相关缓存失效。Changes 在选择、App 激活、操作完成及 Refresh Changes 时重读，不依赖 HEAD 是否变化。不要求持续文件监听。

异步结果绑定工作区和 selection generation，切换选择取消旧读取，不把旧内容展示到新节点；各区域失败互不遮蔽。

## 11. CLI 与内置 skill

### 11.1 命令面

```text
modu-cli workspace inspect [--json]
modu-cli repo list [--json]
modu-cli repo add <url> [--name <display-name>] [--json]
modu-cli repo remove <repo-name> [--execute] [--json]
modu-cli worktree list [--json]
modu-cli worktree create <group> --repo <repo-name>... [--json]
modu-cli worktree update <group> --repo <repo-name>... [--execute] [--json]
modu-cli worktree remove <group> [--repo <repo-name>] [--execute] [--json]
```

全局 `--workspace <path>` 指定已有工作区根；省略时从规范化 cwd 向上匹配有效记录。App 未运行时 CLI 仍可用；首次初始化通过 App。未找到记录或根不存在明确报错，匹配记录无效不回退其他根。inspect/list 只读，无隐式创建或资源修复。

create 先建立 Group 根再追加成员，update 表示完整目标集合，必须通过 `--repo` 提供至少一个仓库；缺少时返回参数错误（退出码 2），即使带有 `--execute` 也不执行任何新增、删除或配置写入。根与新增成员的初始分支名统一为分组名，不提供分支选择参数；已有资源的实际 checkout 保持不变。remove 带 `--repo` 只删除指定成员，不带则先删除全部成员再删除根；需要清空成员并保留根时，逐个使用带 `--repo` 的 remove。删除配置外目标返回 `target-not-configured`；不提供 workspace sync、导入、迁移或修复命令。

### 11.2 授权与输出

新增直接执行；删除和含移除的 update 在交互终端确认一次，`--execute` 直接授权。`--json` 或 stdin 非终端时不读取确认；未授权返回 `confirmation-required` 和含目标、路径、待删除的当前本地分支或不删除分支的原因、风险的 plan，混合 update 的新增也不执行。

`--json` 的 stdout 只输出一个最终文档；进度与整理后的诊断写 stderr。统一外壳为 `schema-version: 1`、`command`、`workspace`、`status`、`reason-code`、`message`、`items`。未定位的 workspace、无请求级错误的 reason-code/message 为 null。

items 按仓库、Group 根或成员列出 resource（kind、repo/group、相对 path）、status、reason-code/message 和 effects。effects 是动作的结构化摘要，含 action、target、state（applied / reverted / unknown），无动作为空数组；reverted 只描述实际清理，无法核实则标 unknown。已移入 Trash 的项附实际 trash-path。资源读取信息放在 data，读取失败不填伪空值。清理失败为 `cleanup-failed`，cause-code 保留原始原因；不提供整体 rollback 状态。

| 总体结果 | status / 退出码 |
| --- | --- |
| 全部目标完成，或只读空列表成功 | success / 0 |
| 有失败/跳过，同时有成功项 | partial-success / 1 |
| 无成功项且失败，或工作区忙 | failed / 1 |
| 全部跳过 | skipped / 1 |
| 缺少删除授权 | confirmation-required / 1 |
| 取消且有未完成项，收尾无失败 | cancelled / 130；已完成项仍为 success |
| 参数、工作区定位或配置加载错误 | failed / 2 |

单项失败可有保留效果，不能为了表达部分效果伪造成功项；取消收尾失败按 failed/partial-success 返回。资源缺失的 inspect 返回非零结果。

稳定 reason-code 按已实现能力定义，至少区分输入/配置错误、workspace-busy、资源缺失/不可用、workspace-commit-required、workspace-ignore-required、路径或身份冲突、branch-in-use、worktree-locked、unmanaged-worktree、网络/认证失败、Git/Trash/配置写入失败、cleanup-failed 和取消。机器字段不随界面语言变化，命令实现时补充对应的契约测试。

### 11.3 modu-workflow

工作区级 skill 只负责调用 CLI：先 inspect 确认上下文，再 list 和执行用户要求的管理动作，统一传 `--json --workspace <root>`。资源异常说明原因并停止相关动作，可用资源不受无关项影响。

删除先预览范围和风险，有明确授权才传 `--execute`，不重复索取已有授权。按结果说明实际完成范围；不直接编辑私有记录、不用 Git/shell 绕过 CLI 的删除和支持边界，不承诺恢复数据。普通代码编辑和非 Modu 目录不触发此 skill。

## 12. 开发与验收

按可运行的纵向流程推进：先完成 CLI 安装与检查、Core 的工作区初始化/加载与最小 App 目录选择入口，再打通 Core/CLI 的添加仓库、创建与删除 Group；随后接主窗口和外部工具，最后完成 Git Browser、手动更新仓库、完整设置和 YAML。初始化直接复用最终 Core 服务，不增设临时 CLI 初始化命令。每一步先验证正常路径及直接相关的失败，不以补齐所有异常修复场景作为开工条件。

测试使用临时目录、本地 bare remote 和故障替身，不访问用户仓库或真实网络；本地 remote 仅为 Git 测试夹具，业务输入仍遵循 URL 限制。优先验证：

1. 配置校验、路径边界、原子保存及 App/CLI 互斥；错误不变成空配置或 clean。首次启用初始化或复用根仓库，检查并补齐标准目录忽略规则；添加仓库补齐仓库名规则，重复执行不重复追加，不暂存或提交，不覆盖用户内容。
2. 仓库和 Group 正常创建/编辑/删除及同名重建；Group 根属于工作区仓库，成员属于各自仓库，分支名均默认使用分组名。首次提交、目标提交中的忽略规则、已跟踪路径冲突、分支占用在创建前检查；不隐式联网、不复制未提交/未跟踪文件。根先创建并保存，成员失败保留根及已成功项；未改变的异常成员不阻止其他成员调整。
3. 删除仓库遇到配置外 worktree 登记（含目录缺失或 locked）或登记读取失败时，GUI/CLI 均在任何删除前阻断，资源和配置不变；确认期间新增配置外登记也被执行前检查拦截，`--execute` 不绕过检查。
4. 根与成员删除同时删除各自实际检出的本地分支，覆盖新建、复用和未合并分支；外部切换分支后不误删分组同名分支，该同名分支缺失不影响已有 worktree 的可用性。detached HEAD 不删除分支，目录缺失时按 Git 登记判断，目录与登记均缺失时只移除声明；确认后分支变化会阻断。创建失败的清理不删除复用分支。删除最后一个成员保留根；删除 Group 必须先成员后根，成员失败不继续删根，根删除失败保留 Group；不留下被父目录删除的成员登记。
5. 配置写入、Git、Trash、认证、超时和取消失败时的必要清理与真实反馈；保存和重读都失败时保留新资源，不误清理。
6. 私有记录和 YAML 成员均为仓库名列表，不保存根或成员分支；满足根仓库提交前置条件的空工作区 YAML 往返保留仓库与分组结构，包括零成员 Group。外部切换分支后导出，再导入时仍按分组名创建成员；部分导入可通过 GUI 的 Add/Create/Edit 补齐，不改变已完成成员的 checkout。设置中的完整工作区导入在非空工作区拒绝且不触碰原内容。
7. 手动更新的远端默认分支识别、只快进、ignored 保护、逐仓库跳过/失败和取消；不修改 linked worktree 文件，已更新引用使相关缓存失效。启动和 App 激活不触发网络更新；Changes 两阶段抵消、特殊路径、冲突，以及 Commits 独立可用性。
8. GUI/CLI 结果一致，工具正确打开工作区、Group 或成员路径；Group 只显示四类适用工具，Fork 打开根 worktree，不聚合成员；切换成员后恢复 Git 详情。首次设置必须成功安装并确认 CLI 可用，失败不可跳过，成功后才可选择工作区和继续；覆盖受管文件不可运行、PATH 缺失、同名目标遮蔽和用户处理后重试通过，检查无需已有工作区。CLI update 缺少 `--repo` 时返回参数错误且无副作用，覆盖带 `--execute`、`--json` 的情况。键盘、VoiceOver、外观和 900×600 窗口可操作。
9. Add Repository 从嵌套 YAML 映射/列表提取完整合法 URL，覆盖 HTTPS、SSH、SCP 风格、无 `.git` 后缀及普通值忽略；解析错误或无合法 URL 时无副作用。向非空工作区追加，重复/已存在项不重复 clone、不改展示名，同名不同 URL 不覆盖，单仓库失败继续、共享条件失败或取消停止；逐项保存、补齐忽略规则，重选文件不重建已完成项。该入口不恢复 Group，不改变设置中完整工作区导入的空工作区限制。

完成验收以“首次设置 → 添加仓库 → 用户提交工作区 .gitignore → 创建/编辑 Group → 打开外部工具 → 查看 Changes/Commits → 更新仓库 → 删除”的真实本地流程为主，再覆盖设置和 CLI。资源异常只要求安全阻断、清楚原因与 Reload，不验收自动修复。

代码改动运行 `./script/build_and_run.sh --verify`；该脚本只验证构建及 App 进程启动，行为需要相应单元、Git 集成、CLI 或 UI 测试。纯文档变更检查链接、规则一致性、原型索引和 `git diff --check`。
